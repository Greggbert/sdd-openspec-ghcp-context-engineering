Appendix D — OpenSpec schema.yaml and Template Reference

OpenSpec uses Schemas to configure how an OpenSpec workflow executes. This appendix can help when you need to read or change an OpenSpec workflow. It covers the fields in schema.yaml, the dependency rules between artifacts, and the way templates become generated change files.

D.1 Schema fields

An OpenSpec schema defines a planning workflow in YAML. It names the workflow, lists the artifacts it produces, and describes the handoff from planning to implementation. In the built-in spec-driven schema, the default sequence is explicit: proposal leads to specs and design, and tasks depends on both before implementation can begin.

The top-level fields are:

Field Type Required? Effect
name string Yes Names the schema. OpenSpec uses the schema directory as the lookup key, even if this value differs.
version positive integer Yes Records the schema revision. It does not change OpenSpec behavior by itself.
description string No Describes the workflow when schemas are listed.
artifacts non-empty list Yes Declares the planning artifacts and their dependencies.
apply mapping No Defines what must be complete before implementation starts and, optionally, which task file tracks progress.

Each entry in artifacts defines one document or one set of documents:

Field Type Required? Effect
id unique string Yes Identifies the artifact. Other artifacts and apply use this value in requires.
generates relative path or glob Yes Tells OpenSpec where the artifact is written inside the change folder. For example, specs/**/*.md can produce one spec per capability.
description string Yes Labels the artifact in the guidance given to the agent.
template relative path Yes Selects the Markdown template under the schema’s templates/ directory.
instruction string No Gives the agent artifact-specific guidance, such as whether the document explains why, what, or how.
requires list of artifact IDs No Makes this artifact wait until the named artifacts are complete. The default is an empty list.

It is useful to treat requires as a dependency graph rather than a suggested reading order. OpenSpec marks an artifact ready only after every dependency is complete. It rejects missing IDs, duplicate IDs, and dependency cycles. When several artifacts are ready at once, their order in artifacts determines which one OpenSpec returns first.

The generates value is relative to the active change directory. proposal.md therefore produces openspec/changes/<change-name>/proposal.md, while specs/**/*.md matches Markdown files below that change’s specs/ directory. Completion is structural: OpenSpec checks that the expected file exists, or that a glob matches at least one file. The check does not evaluate the document’s content.

The optional apply block controls the planning-to-implementation handoff. Its requires field names the artifacts that must exist before apply is ready. Its tracks field points to a relative Markdown file in the change directory, normally tasks.md. OpenSpec uses task checkboxes in that file to report whether work is blocked, ready, or complete. An optional instruction replaces the built-in guidance sent to the implementation agent.

The default workflow has this essential shape:

name: spec-driven
version: 1
description: Default OpenSpec workflow - proposal -> specs -> design -> tasks
artifacts:
  - id: proposal
    generates: proposal.md
    description: Initial proposal document outlining the change
    template: proposal.md
    requires: []
  - id: specs
    generates: specs/**/*.md
    description: Detailed specifications for the change
    template: spec.md
    requires:
      - proposal
  - id: design
    generates: design.md
    description: Technical design document with implementation details
    template: design.md
    requires:
      - proposal
  - id: tasks
    generates: tasks.md
    description: Implementation checklist with trackable tasks
    template: tasks.md
    requires:
      - specs
      - design
apply:
  requires:
    - tasks
  tracks: tasks.md

The example omits the longer agent instructions. The fields serve different purposes: description labels the artifact, template supplies its output shape, and instruction explains what the agent should produce. A changed dependency changes the workflow; a changed template changes the starting structure of every new artifact created from it.

D.2 Template structure

A schema directory contains schema.yaml and a templates/ directory. OpenSpec resolves the template value in each artifact entry relative to that directory:

openspec/schemas/spec-driven/
├── schema.yaml
└── templates/
    ├── proposal.md
    ├── spec.md
    ├── design.md
    └── tasks.md

Templates are Markdown skeletons rather than files copied into the change directory. OpenSpec gives the selected template to the agent as its expected output format. The agent fills that structure and writes the result at the path named by generates.

In the default schema, the mapping is:

Artifact Template Generated path Purpose
proposal proposal.md proposal.md Explains why the change is needed, what it changes, its capabilities, and its impact.
specs spec.md specs/<capability-path>/spec.md Defines observable behavior through requirements and scenarios.
design design.md design.md Explains how the change will be implemented, including decisions, risks, and trade-offs.
tasks tasks.md tasks.md Breaks the implementation into ordered, checkable work items.

The specs entry is the exception to the one-file pattern. It allows a change to produce one delta specification for each capability named by the proposal. The proposal establishes the reason and scope, the spec files define behavior, the design records the technical approach, and the task list turns the plan into work the apply phase can track. Keeping these roles separate helps prevent implementation details from replacing requirements.

When a team needs different documents or a different sequence, it can create a project schema under openspec/schemas/<name>/, edit schema.yaml and the matching templates, and run openspec schema validate <name> before using it. Forking the built-in spec-driven schema copies its schema definition, templates, and instructions into a project-owned directory. A custom template changes the structure of future artifacts; a schema dependency changes which artifacts can be drafted and when. Built-in schemas ship with OpenSpec, so forking one before editing it is preferable to modifying the package copy.
