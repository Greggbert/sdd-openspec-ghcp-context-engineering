Appendix B — OpenSpec Reference

B.1 OpenSpec CLI Command Reference

This section offers a quick reference for the openspec CLI commands used throughout the book. For OpenSpec slash commands, see the next section. The CLI command names and examples are current as of OpenSpec CLI 1.13.1. Since your installed version may differ, you may want to run openspec --help or openspec <command> --help to check the syntax available to you.

The CLI helps manage the files and relationships that make a change reviewable. Decisions about a change’s scope and the quality of its requirements remain with the people reviewing the work.

B.1.1 Typical workflow

  1. You might run openspec init once in a project, then use openspec update when the generated instruction files need to catch up.
  2. To begin a change, use openspec new change <name>, then inspect its artifact status with openspec status --change <name>.
  3. You can use openspec list, openspec show, openspec context, and openspec instructions to inspect the repository and work out what an agent needs next.
  4. Before treating the change as ready, consider running openspec validate <name>. In CI, openspec validate --all may be a better fit when the repository is the unit of validation.
  5. After implementation and verification, you can run openspec archive <name>. Archiving updates the main specifications and moves the completed change out of the active work area.

OpenSpec reports failures through the process exit status, which makes commands such as validate suitable for scripts and CI. The CLI help does not promise a numbered list of exit codes, so this reference does not invent one. In a pipeline, treat a nonzero status as a failed check and preserve the command output as the diagnostic.

B.1.2 Core commands

The commands below cover the operations most projects use regularly. The --json options can help when another tool needs to consume a result, but reading the Markdown artifacts still matters during review.

Command Purpose Useful options
openspec init [path] Initialize OpenSpec in a project and write the selected tool instruction files. --tools all, --tools github-copilot, --language <language>, --profile <profile>, --force
openspec update [path] Update OpenSpec instruction files after the CLI or tool configuration changes. --force
openspec new change <name> Create a new change directory using the selected workflow schema. --description <text>, --goal <text>, --schema <name>, --store <id>, --json
openspec list List active changes. --changes, --specs, --sort recent|name, --json, --store <id>
openspec show [item-name] Display a change or specification. --type change|spec, --json, --diff, --deltas-only, --store <id>
openspec status --change <id> Show which artifacts are complete for a change. --all, --schema <name>, --json, --store <id>
openspec validate [item-name] Validate a change or specification. --all, --changes, --specs, --strict, --json, --type change|spec, --store <id>
openspec archive [change-name] Archive a completed change and update the main specifications. --yes, --skip-specs, --no-validate, --json, --store <id>
openspec doctor Report relationship health for the resolved OpenSpec root. --json, --store <id>

The command names reflect two related interfaces. openspec new change creates a change. The older grouped forms, openspec change show, openspec change list, and openspec change validate, can inspect and validate changes. Since the help output marks openspec change list as deprecated, new scripts are better served by the top-level list, show, and validate commands.

For a quick inspection of a repository, you could start with:

openspec list
openspec status --all
openspec doctor

For a CI (continuous integration) check that covers both active and archived material, choose the narrowest validation that matches the pipeline’s purpose. openspec validate --all validates all changes and specifications, while openspec validate --archived checks that archived changes have completed tasks.

B.1.3 Store and workset commands

Stores and worksets address different needs. You can think of a store as a standalone OpenSpec repository registered on the local machine, giving several related projects a shared place for specifications and changes. A workset is a personal, local view that composes folders for a working session. Removing a workset does not remove its member folders.

Command Purpose Useful options
openspec store setup [id] Create and register a local store. --path <path>, --remote <url>, --init-git, --no-init-git, --json
openspec store register [path] Register an existing local store. --id <id>, --yes, --json
openspec store list List stores registered on this machine. --json
openspec store doctor [id] Check a store’s registration and metadata. --json
openspec store unregister <id> Forget a registration without deleting the files. --json
openspec store remove <id> Forget a registration and delete its local folder. --yes, --json
openspec context Print the working context for the resolved OpenSpec root. --json, --store <id>, --code-workspace <path>, --force
openspec workset create [name] Save a named view of project folders. Repeat --member <path>; optionally use --tool <id> and --json
openspec workset list Show saved worksets and their members. --json
openspec workset open <name> Open a saved workset in its preferred tool. --json
openspec workset remove <name> Delete a saved workset without touching member folders. --json

When the working root should come from a registered store rather than the current project, you can add --store <id> to commands that support it. If shared context is missing or unexpectedly empty, it may help to run openspec store doctor first. That checks the registration boundary before you inspect individual artifacts.

WarningOpenSpec Stores are still in BETA

Please keep in mind the OpenSpec Stores feature is still in BETA release and may change before they are released as a production feature in OpenSpec.

B.2 GitHub Copilot Commands and OpenSpec Skills

OpenSpec names each workflow by its Agent Skill, while the command a developer types depends on the agent harness running it. This section covers GitHub Copilot inside VS Code, IntelliJ IDEA, and GitHub Copilot CLI. VS Code and IntelliJ IDEA use GitHub Copilot’s prompt-file integration. Because GitHub Copilot CLI does not read .github/prompts/, the installed skills are the appropriate option there.1

The appropriate integration can install the relevant files when you initialize the repository, for example with openspec init --tools github-copilot.2 The table uses the current OPSX command form for the Copilot extensions and the Agent Skill form for Copilot CLI. OpenSpec documents the command pattern using the apply workflow; the other workflows appear to follow the same host-specific naming pattern.3

OpenSpec action When to use it VS Code IntelliJ IDEA GitHub Copilot CLI
explore Investigate an idea, existing behavior, or an unclear requirement before creating a change proposal. It is a thinking step and does not implement code. /opsx-explore <Topic> /opsx-explore <Topic> /openspec-explore <Topic>
propose Turn the agreed problem into a change proposal and generate its planning artifacts. /opsx-propose <change-name> /opsx-propose <change-name> /openspec-propose <change-name>
apply Implement the tasks in an existing proposal after reviewing its requirements and design. /opsx-apply <change-name> /opsx-apply <change-name> /openspec-apply-change <change-name>
sync Merge implemented delta requirements into openspec/specs/ while leaving the change proposal open. Use this when the specification is ready to become the current baseline but the change still needs follow-up work. /opsx-sync <change-name> /opsx-sync <change-name> /openspec-sync-specs <change-name>
archive Complete a finished change. This merges its deltas into the main specs and moves the change folder into openspec/changes/archive/. /opsx-archive <change-name> /opsx-archive <change-name> /openspec-archive-change <change-name>

B.2.1 Using the matrix

The VS Code and IntelliJ IDEA entries match because both use the GitHub Copilot IDE integration. OpenSpec generates prompt files under .github/prompts/, which the Copilot extension can expose as slash commands in both editors.4

GitHub Copilot CLI uses the skill spelling. For example, the CLI equivalent of /opsx-apply pets-search would be /openspec-apply-change pets-search. The IDE command is not expected to resolve in the CLI because the CLI does not read .github/prompts/.5

You might use the rows as a working loop rather than as mandatory ceremony for every small edit. Explore can help when the problem or existing behavior is unclear. Propose fits once the intended change is understood well enough to record. Apply is available when the proposal is ready to execute. Sync can update the main specification while the change remains open. Archive generally follows verification and completion, when the change is ready to leave the active-work area and its deltas can become part of the lasting specs.6

The terminal CLI is a separate interface. Commands such as openspec init and openspec validate can manage the project and its artifacts from a shell. Slash commands and skills ask an AI coding tool to carry out a workflow using those artifacts. If a workflow is unavailable, it may help to check that the repository is initialized and valid and that the selected host can see the files it expects.

B.3 OpenSpec schema.yaml and Template Reference

OpenSpec uses Schemas to configure how an OpenSpec workflow executes. This section can help when you need to read or change an OpenSpec workflow. It covers the fields in schema.yaml, the dependency rules between artifacts, and the way templates become generated change files.

B.3.1 Schema fields

An OpenSpec schema defines a planning workflow in YAML. It names the workflow, lists the artifacts it produces, and describes the handoff from planning to implementation. In the built-in spec-driven schema, the default sequence is explicit: proposal leads to specs and design, and tasks depends on both before implementation can begin.

The top-level fields are:

Field Type Required? Effect
name string Yes Names the schema. OpenSpec uses the schema directory as the lookup key, even if this value differs.
version positive integer Yes Records the schema revision. It does not change OpenSpec behavior by itself.
description string No Describes the workflow when schemas are listed.
artifacts non-empty list Yes Declares the planning artifacts and their dependencies.
apply mapping No Defines what must be complete before implementation starts and, optionally, which task file tracks progress.

Each entry in artifacts defines one document or one set of documents:

Field Type Required? Effect
id unique string Yes Identifies the artifact. Other artifacts and apply use this value in requires.
generates relative path or glob Yes Tells OpenSpec where the artifact is written inside the change folder. For example, specs/**/*.md can produce one spec per capability.
description string Yes Labels the artifact in the guidance given to the agent.
template relative path Yes Selects the Markdown template under the schema’s templates/ directory.
instruction string No Gives the agent artifact-specific guidance, such as whether the document explains why, what, or how.
requires list of artifact IDs No Makes this artifact wait until the named artifacts are complete. The default is an empty list.

It is useful to treat requires as a dependency graph rather than a suggested reading order. OpenSpec marks an artifact ready only after every dependency is complete. It rejects missing IDs, duplicate IDs, and dependency cycles. When several artifacts are ready at once, their order in artifacts determines which one OpenSpec returns first.

The generates value is relative to the active change directory. proposal.md therefore produces openspec/changes/<change-name>/proposal.md, while specs/**/*.md matches Markdown files below that change’s specs/ directory. Completion is structural: OpenSpec checks that the expected file exists, or that a glob matches at least one file. The check does not evaluate the document’s content.

The optional apply block controls the planning-to-implementation handoff. Its requires field names the artifacts that must exist before apply is ready. Its tracks field points to a relative Markdown file in the change directory, normally tasks.md. OpenSpec uses task checkboxes in that file to report whether work is blocked, ready, or complete. An optional instruction replaces the built-in guidance sent to the implementation agent.

The default workflow has this essential shape:

name: spec-driven
version: 1
description: Default OpenSpec workflow - proposal -> specs -> design -> tasks
artifacts:
  - id: proposal
    generates: proposal.md
    description: Initial proposal document outlining the change
    template: proposal.md
    requires: []
  - id: specs
    generates: specs/**/*.md
    description: Detailed specifications for the change
    template: spec.md
    requires:
      - proposal
  - id: design
    generates: design.md
    description: Technical design document with implementation details
    template: design.md
    requires:
      - proposal
  - id: tasks
    generates: tasks.md
    description: Implementation checklist with trackable tasks
    template: tasks.md
    requires:
      - specs
      - design
apply:
  requires:
    - tasks
  tracks: tasks.md

The example omits the longer agent instructions. The fields serve different purposes: description labels the artifact, template supplies its output shape, and instruction explains what the agent should produce. A changed dependency changes the workflow; a changed template changes the starting structure of every new artifact created from it.

B.3.2 Template structure

A schema directory contains schema.yaml and a templates/ directory. OpenSpec resolves the template value in each artifact entry relative to that directory:

openspec/schemas/spec-driven/
├── schema.yaml
└── templates/
    ├── proposal.md
    ├── spec.md
    ├── design.md
    └── tasks.md

Templates are Markdown skeletons rather than files copied into the change directory. OpenSpec gives the selected template to the agent as its expected output format. The agent fills that structure and writes the result at the path named by generates.

In the default schema, the mapping is:

Artifact Template Generated path Purpose
proposal proposal.md proposal.md Explains why the change is needed, what it changes, its capabilities, and its impact.
specs spec.md specs/<capability-path>/spec.md Defines observable behavior through requirements and scenarios.
design design.md design.md Explains how the change will be implemented, including decisions, risks, and trade-offs.
tasks tasks.md tasks.md Breaks the implementation into ordered, checkable work items.

The specs entry is the exception to the one-file pattern. It allows a change to produce one delta specification for each capability named by the proposal. The proposal establishes the reason and scope, the spec files define behavior, the design records the technical approach, and the task list turns the plan into work the apply phase can track. Keeping these roles separate helps prevent implementation details from replacing requirements.

When a team needs different documents or a different sequence, it can create a project schema under openspec/schemas/<name>/, edit schema.yaml and the matching templates, and run openspec schema validate <name> before using it. Forking the built-in spec-driven schema copies its schema definition, templates, and instructions into a project-owned directory. A custom template changes the structure of future artifacts; a schema dependency changes which artifacts can be drafted and when. Built-in schemas ship with OpenSpec, so forking one before editing it is preferable to modifying the package copy.

B.4 Further Reading and Community Resources

OpenSpec is open-source software available through its GitHub project and repository. Those resources include an issue queue and discussions, which can provide information about OpenSpec and Spec-Driven Development more generally.

B.4.1 Official documentation

The OpenSpec repository and its documentation are useful starting points. The OPSX workflow describes the workflow used throughout this book. The installation guide covers setup, while supported tools and aliases lists the available integrations.

These sources cover the mechanics of using OpenSpec. Your repository’s proposal, requirements, design, tasks, and verification evidence still provide the context for a specific change. The documentation can explain how a command works, but it cannot decide whether the change is understood well enough to implement or whether the resulting behavior is correct. Your project team remains responsible for the specs, and OpenSpec is more useful when the team understands them fully.

B.4.2 Community schemas and extensions

Community-built schemas and extensions may help when the official OpenSpec workflow does not cover a particular business domain or team practice. They can also provide a working example. It is useful to treat each community-built schema as a proposal to evaluate: read its source and examples, check its maintenance activity and compatibility with your OpenSpec version, and identify the assumptions it makes about your repository and development process.

A small, representative change can provide a useful trial before the schema becomes a team convention. It helps to ask whether its artifacts make requirements easier to review, give Copilot useful context, and produce evidence that the implementation matches the intended behavior. If it adds more SDD ceremony without improving those checks, you might cherry-pick the useful ideas from the community-built schema and leave the rest behind. Recording adopted conventions in the repository gives the next developer a way to understand them.
