Appendix A — Environment Setup and Troubleshooting

A.1 Installing and Updating OpenSpec

A.1.1 Scope

This appendix is intended to cover tested OpenSpec 1.13.1 installation and maintenance procedures for Windows 11 and macOS. The operating-system differences should remain visible rather than being folded into one generic command sequence.

A.1.2 Before installation

  • Readers should first confirm that Node.js 24.19.0 and npm are available.
  • The appendix should describe global npm package locations and the way PATH affects command discovery.
  • Teams may want to decide whether to pin OpenSpec 1.13.1 or allow controlled upgrades.

A.1.3 Install OpenSpec 1.13.1

  • Windows 11 and macOS should have separate terminal instructions.
  • After installation, readers can verify the executable and its version.
  • The tested baseline should include the expected command output.

A.1.4 Inspect the installed version

  • The appendix can show the OpenSpec version command.
  • It can also show how npm reports local and global package versions.
  • The CLI package version should be distinguished from repository-generated integration files.

A.1.5 Upgrade OpenSpec

  • Before changing the team baseline, readers should check the release notes.
  • The global npm package can then be upgraded.
  • The new version should be verified before any repositories are changed.

A.1.6 Update an existing repository

  • An existing repository can be updated with openspec update, using the intended profile and GitHub Copilot integration.
  • Before committing, readers should review changed instructions, prompt files, and Agent Skills.
  • Slash-command discovery should be retested in VS Code and IntelliJ IDEA.
  • The appendix should explain when --force may be appropriate and what needs review afterward.

A.1.7 Verification checklist

  • From a new terminal, the expected CLI version should run.
  • Both repositories should report healthy OpenSpec roots.
  • Generated GitHub Copilot files should match the selected profile.
  • Existing project-owned configuration and artifacts should remain intact.

A.2 Lab Setup

A.2.1 Required tools

Plan to have these available for each participant:

  • Windows 11 or macOS;
  • Git and access to the two prepared Bitbucket repositories;
  • VS Code or IntelliJ IDEA with GitHub Copilot Chat access;
  • OpenSpec 1.13.1;
  • Node.js 24.19.0 and npm;
  • Java 21 and Maven for the Spring Boot 4.1.1 project;
  • Angular 21, Vitest, Playwright, and OpenAPI Generator for the frontend project;
  • Quarto only if participants will render the book locally.

Before the class, check the current OpenSpec installation instructions at https://openspec.dev/docs/installation. Tool versions and package commands can change.

A.2.2 Prepare the exercise repositories

Start by cloning the prepared backend and frontend repositories. It may help to confirm that each repository builds and passes its tests before initializing OpenSpec. The backend owns the OpenAPI contract, and OpenAPI Generator produces the TypeScript Angular client used by the frontend.

cd commercial-truck-search-api
openspec init

cd ../commercial-truck-search-ui
openspec init

When initialization asks which AI tool to configure, select GitHub Copilot. Give each repository its own context instead of copying one configuration into both repositories.

The backend configuration records Java 21, Spring Boot 4.1.1, Maven, Spring Data JPA, H2, test conventions, and ownership of the OpenAPI contract. The frontend configuration records Angular 21, generated-client boundaries, Vitest, Angular component tests, and Playwright.

Review the generated configuration. It can describe stable project facts, but it should not invent database products, deployment platforms, or business rules that the class has not selected.

A.2.3 Preflight check

Before Morning 1, check that:

  1. Both starter applications build and their existing tests pass.
  2. openspec init created the expected project files in both repositories.
  3. GitHub Copilot Chat recognizes the expected OpenSpec commands in VS Code and IntelliJ IDEA.
  4. Each participant knows which commands belong in the terminal and which belong in chat.
  5. Each repository has a clean baseline commit suitable for reset between exercises.

You may want to keep prepared checkpoints for both repositories after each major exercise. That gives participants who miss a step a way to resume from the same accepted specs, contracts, and code state as the rest of the class.

A.3 Troubleshooting OpenSpec

A.3.1 A diagnostic method

For each problem, start with the symptom and a likely cause. Then run the cheapest check that could distinguish between possible causes before choosing a repair. Keep the command output from that check; it may be more useful than repeating a setup step that could change the evidence.

A.3.2 Installation failures

You might see one of these symptoms:

  • openspec cannot be found after npm installation.
  • The terminal resolves a different global npm location than expected.
  • Windows execution policy or macOS permissions prevent the command from running.
  • The installed version differs from the book’s 1.13.1 baseline.

A.3.3 Initialization and update failures

Check whether:

  • OpenSpec initialized a different directory than expected.
  • Existing generated files conflict with the update.
  • The selected GitHub Copilot integration or profile is unavailable.
  • Project-owned configuration changed unexpectedly.

A.3.4 Command discovery failures

You may be dealing with command discovery when:

  • VS Code does not show the expected prompt command.
  • IntelliJ IDEA does not discover the same workflow.
  • A prompt-file command is being confused with an Agent Skill or terminal CLI command.
  • The IDE appears to be using an earlier version of the generated integration files.

A.3.5 Artifact and validation failures

The failure may be in artifact or validation handling when:

  • A change cannot identify its schema.
  • Artifact dependencies remain blocked.
  • Requirements or scenarios fail strict validation.
  • A modified requirement does not match the accepted source requirement.
  • Archive or sync encounters overlapping deltas.

A.3.6 Two-repository failures

Compare the repositories when:

  • Frontend and backend changes use different business terms.
  • The generated Angular client appears stale.
  • The OpenAPI document does not match the backend behavior.
  • A test passes against a different backend or port than the one you intended.

A.3.7 Recovery boundaries

Before regeneration, preserve project-owned specs and active changes. Use version control to inspect generated-file changes. If an OpenSpec defect remains reproducible, report the version, operating system, minimal repository state, command, and complete output.
