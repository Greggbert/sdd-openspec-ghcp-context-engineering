8  Proposing the First Full-Stack Change

Chapter 7 ended with a decision record, not a plan. How might that record become a change that a backend developer, a frontend developer, and Copilot could inspect without replaying the original conversation? Which decisions belong in shared behavior, which belong to one repository, and which should still block implementation?

Follow the unit-number search through OpenSpec’s proposal workflow. Keep the backend and frontend work in separate active changes, then connect them through one reviewed API contract and an explicit handoff. Aim for more than a set of completed Markdown files: give reviewers a cheap way to find scope drift before either repository changes application code.

8.1 Learning objective

Use this chapter to turn a reviewed exploration record into proposal, delta specification, design, and task artifacts for a full-stack capability. By the end, you should be able to explain why two repository changes are preferable here, trace a scenario across both changes, and decide whether the pair is ready for the apply workflow.

8.2 Treat proposal as a review boundary

Do not treat entry into the proposal workflow as evidence that behavior has shipped. Treat it as the point where the team places a specific difference under review while the accepted product behavior remains unchanged.

That distinction should affect how you read the generated files:

Artifact Question for the reviewer Warning sign
proposal.md Why should this change exist, and where should it stop? Classes, methods, or response details appear before the scope has been accepted
specs/<capability>/spec.md What new behavior could a user or client observe? A scenario depends on an unanswered question or names implementation machinery
design.md How might this repository satisfy the behavior? A technical choice quietly creates new user-visible behavior
tasks.md What work and evidence would complete the change? A task has no requirement, or a requirement has no implementation and verification task

Use one proposal when the affected code and review path belong to one repository. For this lab, keep one active change in each repository because the applications have separate code, tests, and ownership boundaries. Connect those changes through the contract dependency instead of hiding the boundary inside one plan.

Before generating files, trace one accepted decision through the artifacts it would affect:

accepted no-match decision
      |
      +-- backend scenario
      |     +-- response-mapping design decision
      |     `-- API test task
      |
      `-- frontend empty-state scenario
          +-- state-handling design decision
          `-- component test task

Use the same trace for valid input, a successful match, and each reviewed error. A broken branch would expose a missing artifact before implementation begins.

8.3 Check whether exploration is ready to become a proposal

Before invoking the proposal workflow, reopen the Chapter 7 decision record. Ask whether a reviewer could write an observable scenario without supplying another assumption.

Use questions such as these:

  • Has the product owner selected exact or partial matching?
  • Has the team agreed on valid input, normalization, and no-match behavior?
  • Has someone approved the fields returned for a match?
  • Have related searches, such as VIN or multi-field search, been accepted or deferred?
  • Does each unresolved item have an owner and a reason it does not block this change?

Do not mistake an assigned owner for permission to ignore a blocking question. If the answer could change a response status, request constraint, result shape, or visible UI state, pause the proposal and get the decision. If the answer affects only a later capability, record the deferral and keep it outside the current scope.

WarningDo not let the example choose the product behavior

The artifact excerpts below illustrate structure. Replace bracketed text with the reviewed decisions from your Chapter 7 record. Do not treat exact matching, an empty result, or any example response shape as accepted merely because it appears in this chapter.

8.4 Name two changes around one capability

Choose names that describe outcomes rather than layers or ticket numbers. For the lab, the two change directories might look like this:

commercial-truck-search-api/
`-- openspec/changes/add-unit-number-search-api/
    |-- proposal.md
    |-- specs/unit-number-search/spec.md
    |-- design.md
    `-- tasks.md

commercial-truck-search-ui/
`-- openspec/changes/add-unit-number-search-ui/
    |-- proposal.md
    |-- specs/unit-number-search/spec.md
    |-- design.md
    `-- tasks.md

Use repository-qualified names when they make cross-repository review notes and build output easier to read. The suffix matters less than using the same capability term, unit-number-search, in both delta specifications.

Record the ownership boundary before asking Copilot to draft either change:

Concern Backend change Frontend change
Accepted search rule Express API-observable behavior Refer to the same rule through user-visible interaction
Wire contract Own and publish the reviewed OpenAPI document Consume a generated client from that document
Validation Enforce the API boundary Offer immediate feedback without weakening or redefining the API rule
Outcomes Return the reviewed success, no-match, and error responses Render loading, result, empty, and error states
Verification Test service and HTTP behavior; inspect the contract Test interaction and rendering; exercise the generated client boundary

Keep request and response types under backend ownership. If the frontend needs a field or error that the backend change does not provide, return that need to the backend proposal instead of editing generated types or inventing a second contract.

8.5 Draft the backend change first

Start in the backend repository because its reviewed contract constrains the frontend handoff. In Copilot Chat, adapt the following prompt to the decisions you actually recorded:

/opsx:propose add-unit-number-search-api

Using the attached Chapter 7 decision record, draft an OpenSpec change for the backend-owned
unit-number search capability.

Please:
- treat only Accepted decisions as requirements;
- preserve Open and Deferred items as dependencies or non-goals;
- keep Java, Spring, persistence, and controller choices out of behavioral requirements;
- include scenarios for each accepted valid-input, match, no-match, and invalid-input outcome;
- record OpenAPI publication and backend verification in the design and tasks; and
- stop and report any decision needed to write an observable scenario.

Do not modify application code or accepted specs.

After generation, inspect the artifact order rather than accepting the folder as one indivisible answer. The proposal should constrain the delta and design; the delta and design should constrain the task list.

8.5.1 Read proposal.md for scope

A compact backend proposal might use this shape:

# Change: Add unit-number search API

## Why

Fleet coordinators need to locate a commercial truck from the unit number supplied in their
workflow.

## What Changes

- Add API behavior for searching by a [reviewed valid unit-number rule].
- Return the [reviewed match and no-match outcomes].
- Publish the request, response, and error behavior in OpenAPI.

## Non-Goals

- VIN search
- Partial or multi-field search
- Frontend rendering behavior

## Dependencies

- The frontend change may generate its client only after review of the published OpenAPI document.

Review the proposal before reading its dependent artifacts:

  • Does Why justify the work without restating the Jira title?
  • Does What Changes name observable scope without selecting endpoint classes or query methods?
  • Do the non-goals prevent plausible but unwanted expansion?

Revise the proposal first if any answer is no.

8.5.2 Read the backend delta for behavior

Insert the approved input, result, and error decisions into the delta. Until then, keep explicit placeholders rather than completing the requirement from repository precedent or convention:

## ADDED Requirements

### Requirement: Search by unit number

The API SHALL accept a unit number that satisfies [the reviewed input rule] and return
[the reviewed result shape].

#### Scenario: Matching truck exists

- **WHEN** a client searches with a valid unit number that matches a truck
- **THEN** the API returns the reviewed truck representation

#### Scenario: No matching truck exists

- **WHEN** a client searches with a valid unit number that matches no truck
- **THEN** the API returns the reviewed no-match response

#### Scenario: Unit number is invalid

- **WHEN** a client searches with a unit number that violates the reviewed input rule
- **THEN** the API returns the reviewed validation response

Check whether each scenario could become an HTTP-level test without knowledge of a Java class. Keep invalid input distinct from valid input with no match, and map every placeholder to an accepted row in the decision record. Leave a missing answer visible rather than replacing it with whatever behavior seems conventional.

8.5.3 Read design.md for consequential choices

Now ask how the backend might satisfy those scenarios. A useful design would usually discuss the request boundary, service and persistence path, error mapping, OpenAPI publication, and test levels. It might record a decision in this form:

## Decision: Publish the backend contract before client generation

Generate the OpenAPI document from the implemented backend boundary and review it against the
delta scenarios before the frontend generates a client.

### Rationale

This order keeps request constraints, result fields, and error responses under backend ownership.

### Consequence

The frontend implementation task remains blocked until the reviewed contract artifact is
available.

Apply a replacement test to each statement. If swapping Spring Data for another persistence mechanism would preserve the statement, keep the mechanism in the design. If changing case handling would alter what a client observes, place that rule in the delta rather than hiding it in a mapper or query decision.

8.6 Draft the frontend change from the contract boundary

Create the frontend proposal only after the backend scope and observable contract have survived review. The OpenAPI document need not exist yet, but the dependency and ownership rule should.

/opsx:propose add-unit-number-search-ui

Using the reviewed backend change and the attached Chapter 7 decision record, draft an OpenSpec
change for the Angular unit-number search interaction.

Please:
- describe user-visible input, loading, result, empty, validation, and error behavior;
- refer to the backend-owned OpenAPI contract instead of duplicating request or response schemas;
- make client generation depend on the reviewed backend contract;
- keep Angular component and service choices in design.md; and
- include tests and a cross-application verification task.

Do not edit generated client files or application code.

Write the frontend scenarios from the user’s interaction rather than restating HTTP mechanics. A representative excerpt might read:

## ADDED Requirements

### Requirement: Search for a truck by unit number

The interface SHALL let a user submit a unit number that satisfies [the reviewed input rule].

#### Scenario: Search is in progress

- **WHEN** the user submits a valid unit number and the request has not completed
- **THEN** the interface shows the reviewed loading state

#### Scenario: No truck is found

- **WHEN** the backend returns the reviewed no-match response
- **THEN** the interface shows the reviewed empty state

#### Scenario: Search fails

- **WHEN** the request returns a reviewed error response
- **THEN** the interface shows the corresponding error state

Apply two checks to this delta. First, confirm that it would still make sense if the generated TypeScript method received a different name. Second, replace broad wording such as “corresponding error state” with the accepted message or state when the decision record provides one.

8.7 Turn the handoff into ordered tasks

Use the full-stack task lists to expose waiting points instead of implying that both agents can work independently from the first minute. Keep repository-local work in its own tasks.md, then repeat the contract handoff in both lists.

The backend sequence might include:

## 1. API behavior

- [ ] 1.1 Implement the reviewed input and search behavior.
- [ ] 1.2 Map match, no-match, and invalid-input outcomes to the reviewed responses.
- [ ] 1.3 Add focused tests for every backend scenario.

## 2. Contract handoff

- [ ] 2.1 Generate the OpenAPI document from the implemented API.
- [ ] 2.2 Compare its constraints, schemas, and responses with the delta specification.
- [ ] 2.3 Publish the reviewed document for the frontend change.

The frontend sequence might include:

## 1. Contract intake

- [ ] 1.1 Obtain the reviewed OpenAPI document from `add-unit-number-search-api`.
- [ ] 1.2 Generate the TypeScript client without hand-editing generated files.

## 2. Search interaction

- [ ] 2.1 Implement the reviewed input and submission behavior.
- [ ] 2.2 Render loading, result, empty, and error states from the generated client response.
- [ ] 2.3 Add focused tests for every frontend scenario.
- [ ] 2.4 Run the cross-application unit-number search path.

Block client generation until the backend publishes a reviewed contract. For every task, name the expected test, generated artifact, or review evidence so that a changed file alone cannot satisfy the checkbox.

8.8 Inspect the generated changes with OpenSpec

Use Copilot Chat to draft and revise the artifacts, then use the terminal to inspect OpenSpec’s view of each change:

openspec status --change add-unit-number-search-api
openspec validate add-unit-number-search-api
openspec show add-unit-number-search-api

Run the corresponding commands in the frontend repository with add-unit-number-search-ui. A successful validation could confirm structure, but it could not confirm that the team chose the right behavior. Read the Markdown and compare it with the source decision record.

When review changes a requirement, update its dependents in the same pass. Recheck error mapping, frontend state handling, tests, and contract generation after a change to the no-match rule. Do not treat the change as coherent until its dependent artifacts agree.

8.9 Review both changes as one capability

Open the backend and frontend changes side by side. Follow behavior from the user’s action to the API response and back to the rendered state:

Review path Backend evidence Frontend evidence Question
Valid submission Request constraint and success scenario Input and submission scenario Do both use the same accepted input rule?
Match Response scenario and schema decision Result-state scenario Can the generated contract supply every displayed field?
No match Reviewed API response Empty-state scenario Does the UI interpret the response without redefining it?
Invalid input Validation response Immediate feedback and response handling Could the UI permit input that the API rejects?
Failure Error contract Error-state scenario Which failures receive distinct user-visible treatment?

Look for drift that valid Markdown would not catch:

  • Does one change say “exact” while the other implies partial matching?
  • Does the frontend expect one result while the backend returns a collection, or the reverse?
  • Does either design introduce normalization absent from the behavioral delta?
  • Does a task add VIN search, pagination, filtering, or another deferred capability?
  • Does every scenario lead to implementation and verification work?

Ask Copilot for a review rather than another rewrite when the drafts are complete:

Review these two OpenSpec changes as one full-stack capability without editing them.

Trace every accepted decision from the Chapter 7 record through the backend and frontend
proposals, delta specifications, designs, and tasks.  Report contradictions, unsupported
assumptions, duplicated contract definitions, missing scenarios, broken dependency order, and
tasks with no requirement.  Cite the artifact and heading for each finding.

Still give the agent’s report a human review. In particular, verify whether a cited “contradiction” represents a real behavioral mismatch or an intentional difference between an API response and its user-facing presentation.

8.10 Hands-on exercise

Create the two unit-number search changes in their respective repositories:

  1. Reopen the Chapter 7 decision record and separate Accepted, Open, and Deferred rows.
  2. Draft add-unit-number-search-api from accepted decisions only.
  3. Review its proposal, delta, design, and tasks in dependency order.
  4. Validate the backend change and record any structural errors.
  5. Draft add-unit-number-search-ui with an explicit dependency on the reviewed backend contract.
  6. Review and validate the frontend change.
  7. Trace each accepted scenario across both repositories with the review table above.
  8. Revise the artifact that owns each defect, then recheck its dependents.

Run the workflow once from VS Code and once from IntelliJ IDEA if both environments are available. Compare the resulting artifacts and validation commands even if prompt discovery or chat entry points differ. Record any difference that changes which repository instructions or OpenSpec skills the agent can see.

Do not apply either change during this exercise. The stopping point should be a reviewed pair of plans whose remaining dependencies are explicit.

8.11 Verification checkpoint

Before moving to Chapter 9, ask:

  • Can every implementation-blocking question from exploration be found as an accepted decision, named dependency, or explicit deferral?
  • Does every requirement describe observable behavior through scenarios?
  • Can each scenario be traced to a design decision when one is needed and to at least one task?
  • Does the backend alone own the OpenAPI wire contract?
  • Must contract review and publication occur before frontend client generation?
  • Do frontend states correspond to the reviewed backend outcomes?
  • Do both openspec validate commands succeed?
  • Has a human reviewer checked behavior and scope beyond structural validation?

Let a “no” send the change back to the artifact that owns the missing information. Repair a missing behavior in the delta, a technical omission in the design, and missing work in the task list. Avoid compensating for an incomplete requirement with a more detailed implementation task.

8.12 What you learned

Use a full-stack proposal to let a reviewer start with an accepted decision, follow it through both repositories, and see the contract handoff that orders the work. Keep the two OpenSpec changes linked without merging separate ownership boundaries or asking the frontend to duplicate the API contract.

Begin Chapter 9 only after that path survives review. Use the backend change’s current artifacts as its first input, not the original Jira sentence and not a remembered chat response.
