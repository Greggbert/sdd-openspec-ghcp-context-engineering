2  The OpenSpec Operating Model

Open an OpenSpec repository during an active change and you may find two accounts of the product. One records the behavior the team accepts now. The other proposes a different state and records the reasoning and work needed to reach it.

Both accounts need to remain visible. If a draft requirement immediately replaced an accepted one, another developer or agent could mistake a proposal for shipped behavior. If the proposal lived only in chat, reviewers could lose its scope or struggle to tell which decisions survived discussion. OpenSpec keeps accepted specifications and active changes in separate directories, then brings them together when the team archives completed work, as shown in the OpenSpec quickstart1.

This separation is the center of the operating model. The rest of the workflow helps a team answer four questions:

  1. What behavior does the system currently promise?
  2. What behavior would this change add, modify, remove, or rename?
  3. How does the team plan to implement and verify that difference?
  4. When has the proposed behavior earned a place in the accepted specifications?

2.1 Learning objective

By the end of this chapter, you should be able to read an OpenSpec repository as a map of accepted behavior and proposed changes. You should also be able to place rationale, requirements, design decisions, and tasks in the artifacts where reviewers can evaluate them.

2.2 Read the tree as two kinds of truth

Start with the two directories that carry most of the workflow:

openspec/
|-- specs/
|   `-- <capability>/
|       `-- spec.md
`-- changes/
    |-- <active-change>/
    |   |-- proposal.md
    |   |-- specs/
    |   |   `-- <capability>/
    |   |       `-- spec.md
    |   |-- design.md
    |   `-- tasks.md
    `-- archive/
        `-- <completed-change>/

Ask a different question of each location:

  • In openspec/specs/, ask, “What behavior has the team accepted as the current baseline?”
  • In openspec/changes/<active-change>/, ask, “What difference is under consideration or implementation?”
  • In openspec/changes/archive/, ask, “Which completed change explains how the baseline reached its current form?”

Suppose the accepted specifications say nothing about searching by truck unit number. A new folder named add-unit-number-search can describe that proposed capability without making it part of the baseline. During review and implementation, the main specs and the change may intentionally disagree because the change contains a delta, not a second complete copy of the product specification.

That temporary disagreement gives reviewers a useful comparison: would applying this delta produce the intended behavior? After the implementation passes review and verification, the archive operation can merge the delta into openspec/specs/ and move the change folder under openspec/changes/archive/.

NoteA repository is not proof

Treat the tree as a record of claims and decisions, not as proof that the software behaves as written. Tests, review, and runtime checks still need to supply evidence. OpenSpec gives that evidence a stated target.

2.3 Follow one change through its artifacts

The default spec-driven schema uses four planning artifacts. Their dependency order follows the decisions a team needs to make: proposal first; specs and design after the proposal; tasks after both; implementation after the task list. The default spec-driven schema reference2 documents these roles and the conditions under which specs or design may be skipped.

                         +-- delta specs --+
proposal.md -------------+                  +-- tasks.md -- apply
                         +-- design.md -----+

The dependency order exposes omissions. If the task list requires an API decision that does not appear in the design, pause before coding. If a design choice changes user-visible behavior but no requirement records it, return to the delta spec. If a delta introduces a capability that the proposal never names, revisit the proposal’s scope.

2.3.1 Proposal: why this change, and how far does it reach?

Use proposal.md to frame the decision. For unit-number search, it might identify the need for exact search, name the affected capability, describe the impact on the backend and frontend, and exclude partial matching from the first change.

A controller class, SQL predicate, or Angular component probably does not belong here. Those details pull the proposal toward implementation before reviewers have agreed on the problem and scope.

A useful proposal should let a reviewer challenge the change at low cost:

  • Does this solve the right problem?
  • Is the proposed capability too broad or too narrow?
  • Which existing capabilities would change?
  • What would remain outside the change?

2.3.2 Delta spec: what observable behavior would change?

Place behavioral differences under the change’s specs/ directory, with one spec.md for each capability named by the proposal. OpenSpec delta sections distinguish ADDED, MODIFIED, REMOVED, and RENAMED requirements. Requirements and scenarios describe what a user or another system could observe, not the code structure that might produce it.

For the running example, a delta could say that a valid 15-character unit number returns exact matches. Its scenarios could cover a match, no match, and invalid input. The delta need not name a Spring repository method or an Angular form control unless that name is part of an external contract.

When a statement feels misplaced, use a replacement test: could the team replace Spring Data with another persistence mechanism while preserving the statement? If so, the statement may describe behavior and belong in the spec. If the replacement would make the statement irrelevant while behavior stayed the same, move it to the design or task list.

2.3.3 Design: how might the implementation satisfy the behavior?

Use design.md when the technical approach deserves review before coding. Cross-repository contracts, a new dependency, data-model changes, security constraints, migrations, or a consequential trade-off may justify it. A small change with an obvious implementation may not.

For unit-number search, the design might choose an endpoint shape, assign validation responsibilities between Angular and Spring Boot, or record how both repositories will keep response semantics consistent. It may also preserve rejected alternatives and their costs so that a later agent does not reopen a settled choice without new evidence.

The design may explain how to satisfy the proposed behavior, but it should not quietly create more behavior. If the design makes unit numbers case-insensitive, users or clients can observe that choice, so the delta spec needs the rule too.

2.3.4 Tasks: what work remains, and in what order?

Turn the reviewed behavior and approach into checkable work in tasks.md. The apply phase tracks Markdown checkboxes, so each task should name an outcome that an agent can complete and a reviewer can inspect.

For example:

## 1. Backend search contract

- [ ] 1.1 Add request validation for the accepted unit-number rules.
- [ ] 1.2 Implement exact-match search and response mapping.
- [ ] 1.3 Add tests for match, no-match, and invalid-input scenarios.

A checked box records claimed progress, not verification evidence. A test result, review, or runtime observation must support the claim.

2.4 Move through the loop with review points

The OpenSpec quickstart presents a five-step loop: explore, propose, review, apply, and archive. Optional skills may add explicit update, sync, and verify operations, but the same review points remain useful. The OpenSpec skills reference3 distinguishes the core skills from optional profile-installed skills and states what each skill may create or change.

2.4.1 Explore without pretending the plan is settled

Use exploration to inspect the codebase, find existing behavior, compare options, and surface unanswered questions. In the unit-search change, exploration might reveal that the backend already normalizes identifiers while the frontend validates only length. That finding could change the proposal, but exploration need not create artifacts or code.

Stay in exploration while an unanswered question could change scope or behavior. Move to proposal once the team can state the problem and the affected capabilities without asking the agent to fill gaps silently.

2.4.2 Propose, then review the artifacts

Proposal turns the idea into reviewable files. Read them before implementation in an order that follows their dependencies:

  1. Read proposal.md for purpose, scope, and affected capabilities.
  2. Read the delta specs for observable behavior and edge cases.
  3. Read design.md, when present, for technical decisions and trade-offs.
  4. Read tasks.md for coverage, dependency order, and stopping points.

When review finds a defect, change the artifact that owns the decision and then inspect its dependents. A revised requirement may require a design change; a revised design may require different tasks. Editing only the task list could leave Copilot with contradictory instructions.

2.4.3 Apply from the plan, but allow the plan to be wrong

During apply, the agent reads the change artifacts, implements pending tasks, and marks completed checkboxes. This supports work across chat sessions because progress and intent remain in the repository instead of one context window.

Do not force implementation through a contradiction. If the codebase disproves a design assumption or exposes missing behavior, stop and revise the affected artifact. An active change can evolve; its first draft does not have to survive contact with the code.

2.4.4 Verify against the change, not only the task list

Before archive, compare the delta’s required behavior with the implementation and the evidence from tests or inspection. A complete task list with an unimplemented scenario should block archive. So should passing tests that encode behavior the team never accepted.

Verification may use OpenSpec’s optional verification skill, project test commands, manual checks, or a combination suited to the risk. Whatever the mechanism, check that each requirement has evidence and that the implementation did not introduce behavior outside the reviewed scope.

2.4.5 Sync or archive when the baseline should change

Use sync when accepted specifications should absorb a delta while the change remains active. Use archive when the change is complete and its folder can move into completed history. Archive can synchronize outstanding deltas before moving the folder. Warnings about incomplete artifacts or tasks should prompt review rather than automatic dismissal.

After archive, a new session should find the current unit-search behavior in the main specification. The archived change should retain the reason, alternatives, and implementation path behind that behavior.

Git still governs collaboration. OpenSpec artifacts are ordinary repository files, subject to branches, pull requests, code review, and commit history. Each team must decide whether archive occurs before or after merge based on its release and review practice.

2.5 Distinguish the interface from the operation

The same workflow may appear through several interfaces. A terminal command such as openspec validate runs the OpenSpec CLI. A prompt such as /openspec-propose invokes an agent skill in the chat host. Some hosts expose shorter aliases, and optional profiles may install more skills.

Before copying a command, ask:

  • Does this text belong in the terminal or in Copilot Chat?
  • Has the repository been initialized with the expected schema and profile?
  • Does this host use the documented skill name or a host-specific alias?
  • Will the operation write planning artifacts, application code, accepted specs, or archive history?

The last question sets a practical guardrail. Explore and verify normally inspect and report. Propose writes planning artifacts. Apply writes code and updates task progress. Sync changes accepted specs. Archive changes accepted specs when needed and relocates the completed change. Confirm the expected write boundary before approving an agent action.

2.6 Hands-on exercise

Classify each statement from the unit-number search change, then name the file that should own it:

  1. Fleet coordinators need to find a truck from the identifier printed on a work order.
  2. A valid unit number contains exactly 15 characters.
  3. The Angular client will reject invalid length before sending a request.
  4. Add controller tests for valid, invalid, match, and no-match cases.
  5. The backend and frontend changes passed their focused test suites.

Some statements need revision before they fit. Statement 1 suggests rationale for proposal.md. Statement 2 describes observable behavior for a delta spec. Statement 3 records an implementation decision for design.md. Statement 4 belongs in tasks.md. Statement 5 supplies verification evidence, which should be recorded with the team’s change or pull-request evidence rather than rewritten as a requirement.

Now move statement 2 into design.md and consider the consequence. A reviewer could no longer approve the behavior without reading the implementation plan, and a later design change could erase a validation rule that users still depend on. Artifact boundaries are review boundaries, not filing conventions.

2.7 Verification checkpoint

Given an unfamiliar OpenSpec tree, try to answer these questions without reading its application code:

  • Which behavior represents the accepted baseline?
  • Which changes remain active, and which capabilities does each touch?
  • Where would you challenge scope, behavior, technical approach, and work coverage?
  • Which artifact dependencies remain incomplete?
  • What evidence would you request before archive?
  • After archive, where would you look for current behavior and where for its history?

If the tree supports those answers, the operating model is doing useful work. If it does not, inspect whether information is missing, duplicated, or stored in an artifact that asks reviewers to make the wrong decision.

2.8 What you learned

Read openspec/specs/ as the accepted behavioral baseline and openspec/changes/ as proposed differences from it. Within a change, the proposal frames purpose and scope, delta specs define observable behavior, the design records consequential implementation choices, and tasks expose the work still to do.

Treat explore, review, apply, verification, sync, and archive as points where the team can inspect or correct the change. The next chapter examines the artifact that most directly constrains an agent’s guesses: testable requirements and scenarios.
